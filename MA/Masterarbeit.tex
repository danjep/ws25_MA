\section{Introduction}\label{sec:intro}
Modern computers come with a set of processors that can run simultaneously. To utilize this for their advantage, developers started to design their programs to use multiple concurrently running threads.
Since these threads might still operate on the same memory it is possible to encounter problems like data-races when executing these programs. Data races occur when two or more threads access the same memory space and at least one of them uses a write operation.
A classic example of two threads can be seen in \cref{fig:example}. \\

\begin{figure}[h]
\centering
\begin{tabular}{c||c}
\multicolumn{2}{c}{\texttt{Init:x=y=0;}} \\[4mm]
\textit{Thread 1:} & \textit{Thread 2:}\\[4mm]

\texttt{x=1;} & \texttt{y=1;} \\
\texttt{a=y;} & \texttt{b=x;} \\
\end{tabular}
\caption{Example of two threads using the same variables. Depending on how the threads are scheduled, the resulting values could feature any combination of $1$ and $0$ for the variables $a$ and $b$.}
\label{fig:example}
\end{figure}

Modern architectures might reorder the commands in these programs in any way for performance reasons and interleave the two threads as they see fit.
Since this might lead to inconsistent results and therefore unpredictable behaviour, programming languages and cpu architectures provide memory consistency models (MCM). If the developer confines themselves to these rules, they get certain guarantees in return.
These memory consistency models describe how threads are allowed to interact with each other when it comes to shared memory. As can be seen in the example, not having a memory consistency model can have serious consequences for the execution of programs. But having a memory consistency model will not automatically get rid of all problems. It is not guaranteed for example that a given model will not produce out-of-thin-air values (oota) \cite{BoeDem14}.
Therefore it is an important issue to verify the functionality of these models which will be the topic of the master's thesis.

\subsection{Memory Consistency Models}\label{sec:MCM}
Memory Consistency Models constitute what programmers and execution environments agree on when it comes to how concurrent programmes are allowed to be executed. They define consistency constraints on execution graphs and provide guarantees for how memory accesses are processed on shared memory.
These consistency constraints can be expressed through relational algebra extended with irreflexivity and emptiness \todo{korrekt ausgedrückt?}. \\
Memory models can roughly be divided into two classes, operational models and axiomatic ones.
Operational models are abstractions of real machines with idealised components and are perceived as being more intuitive \todo{Quelle?}. 
Axiomatic models constrain relations on memory operations to allow or disallow behaviour of programmes. To this end one can understand memory operations as nodes in a graph where the edges are relations between these operations like the \textit{program order} (po) or \textit{read-from} (rf).
While po describes the order of instructions within a single thread, rf depicts for each read which write provides the value that is extracted. \\
Therefore the po relation is given by how the program is written and rf depends on the execution. In \cref{fig:examplegraph,fig:storebuffering} one can see the possible graphs of the example from \cref{fig:example}. \\

Since simulation \cite{Mad+10} and verification \cite{Alg+13} are substantially faster on axiomatic models, research has focussed on this type. 
Axiomatic models are defined in three stages: mapping each instruction onto a mathematical object and defining relations on the events, constructing a set of candidate executions like in \cref{fig:examplegraph,fig:storebuffering} and deciding which executions are valid according to the constraints on the relations. \\
They are typically expressed in the CAT language of \cite{Alg+14} which covers all of relational algebra and established itself as a standard. More on the CAT language in \cref{sec:cat}.\\
To validate that a program is executed according to a given mcm is called \textit{consistency checking} and can be reduced to a certain depth-first search on the execution graph \cite{Kok+23}. A program is consistent with a model if it fulfils all constraints of the model. \\
For consistency checking there exist many automated tools like HERD \cite{Alg+14}, GenMC \cite{KokVaf21} and Dartagnan \cite{Pon+18}. 
The issue this master's thesis deals with is verification of memory consistency models which is a very different problem. According to \cite{GruMey25} it consists of five tasks that an automated verification tool should ideally cover:
The first task is to check generic properties of mcms like permitting no out-of-thin-air values. The second task is to review properties referring to operation's semantics like \textit{barrier monotonicity} (there are fewer possible executions when inserting synchronizations \todo{verifiziere diese Beschreibung}). The next task is to compare models and determine which is stronger. Task four is to create litmus tests that check whether a language or architecture implements a model. The last task is to verify compiler transformations. \\
Since we want to verify the models and not a program, it is important to check properties for every program that could be executed under the model.
For this task there exist two automated tools, KATER \cite{Kok+23} and RAT \cite{GruMey25} which both are not able to handle every possible mcm but only a fragment.




\subsection{The CAT language} \label{sec:cat}

In 2014 Alglave et al. proposed an axiomatic framework for modelling weak memory and the corresponding language CAT \cite{Alg+14} which has since then become the standard for writing memory consistency models. In this case, weakness is defined as accepting a larger number of possible executions of a program than stronger models. Axiomatic models work by constraining relations on so called events. The events are the memory accesses in a program like reads and writes. 

\begin{figure}[h]
\begin{align*}
\langle cat\rangle &:= \langle constraint\rangle \mid \langle cat \rangle~ \langle cat\rangle \\
\langle constraint \rangle &:= \texttt{acyclic } \langle rel \rangle \mid \texttt{irreflexive } \langle rel \rangle \\
\langle rel \rangle &:= \langle base\_rel \rangle \mid \langle rel \rangle . \bangle{rel} \mid \bangle{rel}^* \mid \bangle{rel} \cup \bangle{rel} \mid \bangle{rel} \cap \bangle{rel} \\ &\quad \mid \bangle{rel}^{-1} \mid \bangle{rel}^+ \mid \bangle{rel}? \mid \bangle{base\_set} \times \bangle{base\_set} \mid \textcolor{red}{\bangle{rel}\setminus \bangle{rel} \mid{} \sim\bangle{rel}} \\
\bangle{base\_rel} &:= \text{po} \mid \text{rf} \mid \text{rmw} \mid \text{loc} \mid \text{ext} \mid \text{id} \mid \emptyset \\
\bangle{base\_set} &:= \text{R} \mid \text{W} \mid \text{F} \mid \text{B} \mid \text{M} \mid \text{IW} \mid \text{E}
\end{align*}
\caption{The CAT language when including the red coloured terms, when excluding them it is the fragment called rational CAT. $\bangle{rel}^+$ is the transitive closure, $\bangle{rel}?$ the reflexive closure, $\bangle{rel}^*$ the reflexive and transitive closure, $\sim\bangle{rel}$ the complement \cite{Alg+14}.}   
\label{fig:cat}
\end{figure}

\section{Related Work}\label{sec:kontext}
In the field of memory consistency models current research is aimed at a variety of issues.
One obvious issue is model checking programs for a given memory model \cite{Tun+23,KokVaf21}. 
%In the realm of verification this would be on the program verification level. 
Others might focus on the models themselves and their attributes \cite{LahBok22} or other kinds of models like operational ones \cite{Ior+23,Doh+22}. Additionally, researchers are looking at ways of comparing \cite{Wic+17,Sha+23} and verifying \cite{Kok+23,And+25,Kir+20} memory consistency models.




Some very basic examples for these relations are the \textit{program order} (po) which represents the sequence of events of a single thread and \textit{read-from} (rf), displaying for every read which write determined the value it sees. Upon these and some more base relations, memory consistency models can be expressed with CAT as can be seen in \cref{fig:cat}. \\
Besides axiomatic models, researchers also look at operational ones which are abstractions of actual machines with idealised components \cite{Alg+14}. \\

While the tool that Alglave et al. developed allows to test certain programs in a given memory model, verifying these models is a different issue.
  
For the first task, the memory model in question can be compared to a model that is defined by just that property. The first tool to tackle this and the third task was KATER \cite{Kok+23} which covered only a fragment of CAT that could be transformed into Kleene algebra with tests (KAT). This fragment excluded set difference, complement, intersections, converses and the construction of relations from sets. \\
The next year Koutsouridis et al. presented KATI \cite{Kou+24} which is able to handle converses and some intersections but was not implemented.

The first tool that addressed all intersections as well as inverses and construction of relations from sets (called rational CAT, see \cref{fig:cat}) was RAT (Relational Algebra with Tableaus) which was developed by the supervisors of this master's thesis in 2025 \cite{GruMey25}. Their tool is able to handle the first four tasks of the verification with only the compiler transformations being left as an open issue. In their yet to be published work, they present a logical theory of relations where the unsatisfiability of a formula is equivalent to the model fulfilling a set of assertions.
By transforming the question of $M \subseteq M_{prop}$ into $\overline{M} \cap M_{prop} = \emptyset$ and then a formula $\neg \psi_M \land \psi_{M_{prop}}$ it proves whether the given model is stronger than the condition that is to be tested.
The formula is then decomposed until there exists a satisfying model for the formula or it is deemed unsatisfiable. \\


Today there are many open questions in this field of research. Is it possible to automatically verify the whole of the CAT language or at least more than the rational CAT fragment?
Can the popular models written in CAT be transformed into ones that are written in rational CAT?
Is it possible to verify compiler transformations?
This master's thesis will be about the issue of whether the proof system in \cite{GruMey25} can be improved while sustaining the soundness and completeness.
