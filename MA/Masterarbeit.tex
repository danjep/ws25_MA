\section{Introduction}\label{sec:intro}
Almost every computer that is in use today provides multiple simultaneously running processors. To reap the benefits that multiple processors provide, developers design their programs to use concurrently running threads. 
Since multiple threads may operate on the same memory, it is possible that on some memory location one thread writes a value that another thread needs, but never sees. In \Cref{fig:example} two threads each write a value on a memory location that the other one reads. 
Multiple executions are possible: If thread $T_1$ is executed completely before $T_2$ the result is different to when $T_2$ is executed completely before $T_1$. This is called a \textit{data race}. Data races occur when two or more threads access the same memory space and at least one of them uses a write operation.\\

\centering

\label{fig:example}

Every program that a thread might execute consists of instructions which in turn consist of memory accesses. The instruction \texttt{a=y} for example consists of two operations, reading the value of \texttt{y} and writing the read value to \texttt{a}. These two operations are usually called events.
CPU architectures and compilers may reorder the events in such programs for performance reasons and interleave the two threads as they see fit. Since this permits different executions for the same program depending on the hardware and compiler, programming languages and CPU architectures provide \textit{memory consistency models} (MCM). If the developer confines them selves to the rules of a programming language (e.g. \textit{Data-Race-Freedom}(DRF)), they get certain guarantees in return for how the program will be compiled and executed. The MCM of the language illustrates which rules the compiler needs to respect to keep the semantics of the program. The memory consistency model of a CPU architecture describes how the hardware will behave if it runs a program. For the program to have  the intended semantics, the execution needs to be consistent with both models. Essentially, the MCMs constrain how threads are allowed to interact with each other when it comes to shared memory.

As can be seen in the example, not having a memory consistency model can change the outcome of a program drastically. But having a MCM will not automatically get rid of all problems. 
MCMs are defined by humans and can have bugs. They may not capture the behavior of the architecture correctly or be insufficiently defined. 
Consequently there is research on how MCMs can be verified and how the verification can be done effectively. \todo{hier kommt noch hin was diese MA so machen will.} \Cref{sec:kontext} will show what current lines of research exist in the field of weak memory and especially the work that has been done in verification of MCMs.

\subsection{Memory Consistency Models}\label{sec:MCM}
Memory Consistency Models constitute what programmers and execution environments agree on when it comes to how concurrent programmes are allowed to be executed. They define consistency constraints on execution graphs and provide guarantees for how memory accesses are processed on shared memory.
These consistency constraints can be expressed through relational algebra extended with irreflexivity and emptiness \todo{korrekt ausgedrückt?}. \\
Memory models can roughly be divided into two classes, operational models and axiomatic ones.
Operational models are abstractions of real machines with idealised components and are perceived as being more intuitive \todo{Quelle?}. 
Axiomatic models constrain relations on memory operations to allow or disallow behaviour of programmes. To this end one can understand memory operations as nodes in a graph where the edges are relations between these operations like the \textit{program order} (po) or \textit{read-from} (\rf).
While po describes the order of instructions within a single thread, \rf{} depicts for each read which write provides the value that is extracted. \\
Therefore the po relation is given by how the program is written and \rf{} depends on the execution.
From this, one can deduce that there are multiple possible execution graphs. In \cref{fig:examplegraph,fig:storebuffering} one can see the possible graphs of the example from \cref{fig:example}.

Since simulation \cite{Mad+10} and verification \cite{Alg+13} are substantially faster on axiomatic models, research has focussed on this type. 
Axiomatic models are defined in three stages: mapping each instruction onto a mathematical object and defining relations on the events, constructing a set of candidate executions like in \cref{fig:examplegraph,fig:storebuffering} and deciding which executions are valid according to the constraints on the relations. \\
They are typically expressed in the CAT language of \cite{Alg+14} which covers all of relational algebra and established itself as a standard. More on the CAT language in \cref{sec:cat}.\\
To validate that a program is executed according to a given MCM is called \textit{consistency checking} and can be reduced to a certain depth-first search on the execution graph \cite{Kok+23}. A program is consistent with a model if it fulfils all constraints of the model. \\
For consistency checking there exist many automated tools like HERD \cite{Alg+14}, GenMC \cite{KokVaf21} and Dartagnan \cite{Pon+18}. 
The issue this master's thesis deals with is verification of memory consistency models which is a very different problem. According to \cite{GruMey25} it consists of five tasks that an automated verification tool should ideally cover:
The first task is to check generic properties of MCMs like permitting no out-of-thin-air values. The second task is to review properties referring to operation's semantics like \textit{barrier monotonicity} (there are fewer possible executions when inserting synchronizations \todo{verifiziere diese Beschreibung}). The next task is to compare models and determine which is stronger. Task four is to create litmus tests that check whether a language or architecture implements a model. The last task is to verify compiler transformations. \\
Since we want to verify the models and not a program, it is important to check properties for every program that could be executed under the model.
For this task there exist two automated tools, KATER \cite{Kok+23} and RAT \cite{GruMey25} which both are not able to handle every possible MCM but only a fragment.

\subsection{The CAT language} \label{sec:cat}

In 2014 Alglave et al. proposed an axiomatic framework for modelling weak memory and the corresponding language CAT \cite{Alg+14} which has since then become the standard for writing axiomatic memory consistency models. In this case, weakness is defined as accepting a larger number of possible executions of a program than stronger models. CAT has some built-in base relations that can be used like po, \rf, the \textit{same location} relation \loc, which connects all events of one particular memory location and the \textit{identity} and empty relations \texttt{id} and $0$. Furthermore it provides the constraints \texttt{acyclic}, \texttt{irreflexive} and \texttt{empty} which are sufficient for expressing every desired model and property. 

\begin{figure}[h]
\begin{align*}
\langle cat\rangle &:= \langle constraint\rangle \mid \langle cat \rangle~ \langle cat\rangle \\
\langle constraint \rangle &:= \texttt{acyclic } \langle rel \rangle \mid \texttt{irreflexive } \langle rel \rangle \mid \texttt{empty } \bangle{rel} \\
\langle rel \rangle &:= \langle base\_rel \rangle \mid \langle rel \rangle . \bangle{rel} \mid \bangle{rel}^* \mid \bangle{rel} \cup \bangle{rel} \mid \bangle{rel} \cap \bangle{rel} \\ &\quad \mid \bangle{rel}^{-1} \mid \bangle{rel}^+ \mid \bangle{rel}? \mid \bangle{base\_set} \times \bangle{base\_set} \mid \bangle{rel}\setminus \bangle{rel} \mid{} \sim\bangle{rel} \\
\bangle{base\_rel} &:= \text{po} \mid \text{\rf} \mid \text{rmw} \mid \text{\loc} \mid \text{ext} \mid \text{id} \mid 0 \\
\bangle{base\_set} &:= \text{R} \mid \text{W} \mid \text{F} \mid \text{B} \mid \text{M} \mid \text{IW} \mid \text{E}
\end{align*}
\caption{The CAT language according to \cite{Alg+16}, where $\bangle{rel}^+$ is the transitive closure, $\bangle{rel}?$ the reflexive closure, $\bangle{rel}^*$ the reflexive and transitive closure, $\sim\bangle{rel}$ the complement.}   
\label{fig:cat}
\end{figure}

Besides the given base relations, on can define derived relations in the CAT language like the \textit{coherence order} (\co) which is a total order of writes on the same memory location or \textit{happens-before} (\hb) which relates each event to the ones that occurred before. The derivations can be written with the keyword \texttt{let} and using the operations in \cref{fig:cat} like this:
\[\texttt{let } \text{fr} = \text{\rf}^{-1}\text{.\co} \qquad \texttt{let } \text{\co} = \text{\rf .fr} \qquad \texttt{let } \text{\hb}=\text{po}\cup \text{\co}\cup \text{\rf} \cup \text{fr}\]
The language also includes some base sets of events. These include the set of all events E, all reads (R) and writes (W), initial writes IW and fences F.


\section{Related Work}\label{sec:kontext}
\todo{mehr ausführen was in den verschiedenen Bereichen gemacht wird} \\
There are currently several established lines of research in the field of weak memory. One obvious issue is the \textit{consistency checking} of programs under a given memory model \cite{Tun+23,KokVaf21}. Several automated tools that were developed in the last decade already handle this issue well. Examples are GenMC \cite{KokVaf21}, DARTAGNAN \cite{Pon+18} and HERD \cite{Alg+14}.
Furthermore, there is research on refining stateless model checking \cite{Jon+25}.
%In the realm of verification this would be on the program verification level. 
Some research groups instead examine the models themselves and their attributes \cite{LahBok22} or other the already mentioned operational models \cite{Ior+23,Doh+22}. Additionally, researchers are looking at ways of comparing \cite{Wic+17,Sha+23} and verifying \cite{Kok+23,And+25,Kir+20} memory consistency models which are closely related problems.

The first tool to verify MCMs was KATER \cite{Kok+23} which covered only a fragment of CAT that could be transformed into Kleene algebra with tests (KAT). This fragment excluded set difference, complement, intersections, converses and the construction of relations from sets. \\
Since a lot of MCMs like SC, TSO, Power and Arm8 could be defined without the use of these operations, KATER was already very useful and through the exclusion of complement and intersections the verification becomes PSAPCE-complete instead of EXPSPACE-complete (Kozen Smith, 1996)\cite{KozSmi96,Nak17} \todo{Quelle verifizieren}.
Notably, the fragment of \cite{Kok+23} excludes the definitions of C11 and the Linux Kernel Memory Model (LKMM) \cite{Kou+24}. To include these models and others, intersections are needed.
The next year Koutsouridis et al. presented KATI \cite{Kou+24} which is able to handle converses and some intersections but was not implemented.

The first tool that addressed all intersections as well as inverses and construction of relations from sets (called rational CAT, see \cref{fig:cat}) was RAT (Relational Algebra with Tableaus) which was developed by the supervisors of this master's thesis in 2025 \cite{GruMey25}. Their tool is able to handle the first four tasks of the verification with only the compiler transformations being left as an open issue. In their yet to be published work, they present a logical theory of relations where the unsatisfiability of a formula is equivalent to the model fulfilling a set of assertions.
By transforming the question of $\llbracket M\rrbracket \subseteq \semsof{M_{prop}}$ into $\overline{\semsof{M}} \cap \semsof{M_{prop}} = \emptyset$ and then a formula $\neg \psi_M \land \psi_{M_{prop}}$ it proves whether the given model is stronger than the condition that is to be tested.
The formula is then decomposed until there exists a satisfying model for the formula or it is deemed unsatisfiable. \\


Today there are many open questions in this field of research. Is it possible to automatically verify the whole of the CAT language or at least more than the rational CAT fragment?
Can the popular models written in CAT be transformed into ones that are written in rational CAT?
Is it possible to verify compiler transformations?
This master's thesis will be about the issue of whether the proof system in \cite{GruMey25} can be improved while sustaining the soundness and completeness.
