\section{Introduction}\label{sec:intro}
Almost every computer that is in use today provides multiple simultaneously running processors to satisfy the surging demand for computational power. In order to reap the benefits that multiple processors provide, developers have to design their programs to use concurrently running threads. 
Since multiple threads may operate on the same memory, it is possible that on some memory location one thread writes a value that another thread wants to use, but never sees. In \Cref{fig:example} two threads each write a value on a memory location that the other one reads. 
Multiple different executions are possible: If thread $T_1$ is executed completely before $T_2$ the result is different to when $T_2$ is executed completely before $T_1$. The situation where two or more threads access the same memory space and at least one of them uses a write operation i called a \textit{data race}. This is what makes the different executions possible.\\

Every program that a thread might execute consists of instructions which in turn consist of memory accesses. The instruction \texttt{a=y} for example consists of two operations, reading the value of \texttt{y} and writing the read value to \texttt{a}. These two operations are usually called events.
CPU architectures and compilers may reorder the events in such programs for performance reasons and interleave the two threads as they see fit. 
Since this permits different executions for the same program, programmers need to be careful about their code. Programming languages and CPU architectures provide \textit{memory consistency models} (MCM) in order to give them some orientation about how their code will be handled by the compiler and hardware.
Since the language MCM determines the semantics of a program, developers need to confine themselves to the rules of the language (e.g. \textit{Data-Race-Freedom} (DRF)). In return they get certain guarantees for how the program will be compiled and executed. 
The memory consistency model of a CPU architecture describes how the hardware will behave if it runs the instructions of the compiled program. For the program to have the intended semantics, the code needs to be respect the rules of the language MCM and the compiled instructions have to be consistent with the hardware MCM. 
Essentially, the MCMs  determine which update to the shared memory is seen by which thread at what time.

As can be seen in the example, the memory consistency model can change the outcome of a program drastically. But the presence of a MCM may not guarantee the intended behaviour. 
MCMs are defined by humans and can have bugs. They may not capture the behavior of the architecture correctly or be insufficiently defined. 
Consequently there is research on how MCMs can be verified and how the verification can be done effectively. \todo{hier kommt noch hin was diese MA so machen will.} \Cref{sec:kontext} will show what current lines of research exist in the field of weak memory and especially the work that has been done in verification of MCMs.

\subsection{Memory Consistency Models}\label{sec:MCM}
Memory Consistency Models constitute what programmers and execution environments agree on when it comes to how concurrent programs are allowed to be executed. They define consistency constraints on execution graphs and provide guarantees for how memory accesses are processed on shared memory.
Memory models can roughly be divided into two classes, operational models and axiomatic ones.
Operational models are abstractions of real machines with idealized components and may be perceived as being more intuitive. 
Axiomatic models constrain relations on memory operations to allow or disallow behavior of programs. To this end one can understand memory operations as nodes in a graph where the edges are relations between these operations like the \textit{program order} (\po) or \textit{read-from} (\rf).
While \po{} describes the order of instructions within a single thread, \rf{} depicts for each read which write provides the value that is extracted. \\
Therefore the \po{} relation is given by how the program is written and \rf{} depends on the execution.
From this, one can deduce that there are multiple possible execution graphs. In \Cref{fig:examplegraph,fig:storebuffering} one can see the possible graphs of the example from \Cref{fig:example}.

Since simulation \cite{Mad+10} and verification \cite{Alg+13} are substantially faster on axiomatic models, research has focused on this type. 
Axiomatic models are defined in three stages: mapping each instruction onto a mathematical object and defining relations on the events, constructing a set of candidate executions like in \Cref{fig:examplegraph,fig:storebuffering} and deciding which executions are valid according to the constraints on the relations. \\
They are typically expressed in the CAT language of \cite{Alg+14} which covers all of relational algebra and established itself as a standard. More on the CAT language in \Cref{sec:cat}.\\
To validate that a program is executed according to a given MCM is called \textit{consistency checking} and can be reduced to a certain depth-first search on the execution graph \cite{Kok+23}. A program is consistent with a model if it fulfills all constraints of the model. \\
For consistency checking there exist many automated tools like HERD \cite{Alg+14}, GenMC \cite{KokVaf21} and Dartagnan \cite{Pon+18}. 
The issue this master's thesis deals with is verification of memory consistency models which is a very different problem. According to \cite{GruMey25} it consists of five tasks that an automated verification tool should ideally cover:
The first task is to check generic properties of MCMs like permitting no out-of-thin-air values. The second task is to review properties referring to operation's semantics like \textit{barrier monotonicity} (there are fewer possible executions when inserting synchronizations). The next task is to compare models and determine which is stronger. Task four is to create litmus tests that check whether a language or architecture implements a model. The last task is to verify compiler transformations. \\
Since we want to verify the models and not a program, it is important to check properties for every program that could be executed under the model.
For this task there exist two automated tools, KATER \cite{Kok+23} and RAT \cite{GruMey25} which both are not able to handle every possible MCM but only a fragment.

The most intuitive and restrictive MCM is Lamport's \textit{Sequential Consistency} (SC) \cite{Lam79} which guarantees that operations are executed as if they were in some sequential order and the operations of each thread follow \po .
Later, models that are less restrictive like \textit{SC per Location} (also known as \textit{Coherence} or \textit{UNIPROC}) and \textit{Total Store Order} (TSO)\cite{SPA92} were developed to allow for more optimization by the hardware.




\subsection{The CAT language} \label{sec:cat}

In 2014 Alglave et al. proposed an axiomatic framework for modelling weak memory and the corresponding language CAT \cite{Alg+14} which has since then become the standard for writing axiomatic memory consistency models. In this case, weakness is defined as accepting a larger number of possible executions of a program than stronger models. CAT has some built-in base relations which include the already mentioned \po{} and \rf. Besides those, there are the \textit{same location} relation \loc, which connects all events of one particular memory location, the \textit{external} relation \ext which includes all pairs of events that originate from different threads, the \textit{read-modify-write} relation \rmw{} that relates a read event with a write event of the same memory location that can be interpreted as an atomic operation and the \textit{identity} and empty relations \texttt{id} and $0$. Furthermore it provides the constraints \texttt{acyclic}, \texttt{irreflexive} and \texttt{empty} which are sufficient for expressing every desired model and property. 

\begin{figure}[h]
\begin{align*}
\langle cat\rangle &:= \langle constraint\rangle \mid \langle cat \rangle~ \langle cat\rangle \\
\langle constraint \rangle &:= \texttt{acyclic } \langle rel \rangle \mid \texttt{irreflexive } \langle rel \rangle \mid \texttt{empty } \bangle{rel} \\
\langle rel \rangle &:= \langle base\_rel \rangle \mid \langle rel \rangle . \bangle{rel} \mid \bangle{rel}^* \mid \bangle{rel} \cup \bangle{rel} \mid \bangle{rel} \cap \bangle{rel} \\ &\quad \mid \bangle{rel}^{-1} \mid \bangle{rel}^+ \mid \bangle{rel}? \mid \bangle{base\_set} \times \bangle{base\_set} \mid \bangle{rel}\setminus \bangle{rel} \mid{} \sim\bangle{rel} \\
\bangle{base\_rel} &:= \textsf{po} \mid \text{\rf} \mid \textsf{rmw} \mid \text{\loc} \mid \textsf{ext} \mid \textsf{id} \mid \textsf{0} \\
\bangle{base\_set} &:= \text{R} \mid \text{W} \mid \text{F} \mid \text{B} \mid \text{M} \mid \text{IW} \mid \text{E}
\end{align*}
\caption{The CAT language according to \cite{Alg+16}, where $\bangle{rel}^+$ is the transitive closure, $\bangle{rel}?$ the reflexive closure, $\bangle{rel}^*$ the reflexive and transitive closure, $\sim\bangle{rel}$ the complement. Furthermore, $\textsf{0}$ denotes the empty relation and \id the identity relation.}   
\label{fig:cat}
\end{figure}

Besides the given base relations, one can define derived relations in the CAT language like the \textit{coherence order} (\co) which is a total order of writes on the same memory location or \textit{happens-before} (\hb) which relates each event to the ones that occurred before \cite{Lam78}. The derivations can be written with the keyword \texttt{let} and using the operations in \Cref{fig:cat} like this:
\[\texttt{let } \fr = \text{\rf}^{-1}\text{.\co} \qquad \texttt{let } \text{\co} = \text{\rf .\fr} \qquad \texttt{let } \text{\hb}=\textsf{po}\cup \text{\co}\cup \text{\rf} \cup \text{\fr}\]
The language also includes some base sets of events. These include the set of all events E, all reads (R) and writes (W), initial writes IW and fences F. \\
The Memory Models from the last section can be formalized according to \cite{GruMey25,Kou+24} like this:
\begin{align*}
&\text{(SC) } \hfill &\texttt{acyclic }\hb \\
&\text{(TSO) } \hfill &\texttt{irreflexive }(\po \setminus (W\times R) \cup (\rf \cap \textsf{ext}) \cup \co \cup \fr)^+ \\
&\text{(SC per Location)} \hfill &\texttt{acyclic } (\po \cap \loc) \cup (\rf \cup \co \cup \fr)
\end{align*}  


\section{Related Work}\label{sec:kontext}

There are currently several established lines of research in the field of weak memory. One obvious issue is the \textit{consistency checking} of programs under a given memory model \cite{Tun+23,KokVaf21}. Several automated tools that were developed in the last decade already handle this issue well. Examples are GenMC \cite{KokVaf21}, DARTAGNAN \cite{Pon+18} and HERD \cite{Alg+14}.
Furthermore, there is research on refining stateless model checking \cite{Jon+25}.
%In the realm of verification this would be on the program verification level. 
Some research groups instead examine the models themselves and their attributes \cite{LahBok22} and others the already mentioned operational models \cite{Ior+23,Doh+22}. Additionally, researchers are looking at ways of comparing \cite{Wic+17,Sha+23} and verifying \cite{Kok+23,And+25,Kir+20} memory consistency models which are closely related problems.

The first tool to verify MCMs was KATER \cite{Kok+23} which covered only a fragment of CAT that could be transformed into Kleene Algebra with Tests (KAT). This fragment excluded set difference, complement, intersections, converses and the construction of relations from sets. \\
Since a lot of MCMs like SC, TSO, Power and Arm8 could be defined without the use of these operations, KATER was already very useful and through the exclusion of complement and intersections the verification becomes PSAPCE-complete instead of EXPSPACE-complete \cite{KozSmi97,Nak17}.
Notably, the fragment of \cite{Kok+23} excludes the definitions of C11 and the Linux Kernel Memory Model (LKMM) \cite{Kou+24}. To include these models and others, intersections are needed.
The next year Koutsouridis et al. presented KATI \cite{Kou+24} which is able to handle converses and some intersections but was not implemented.

The first tool that addressed all intersections as well as inverses and construction of relations from sets (called rational CAT, see \Cref{fig:cat}) was RAT (Relational Algebra with Tableaus) which was developed by the supervisors of this master's thesis in 2025 \cite{GruMey25}. Their tool is able to handle the first four tasks of the verification with only the compiler transformations being left as an open issue. In their yet to be published work, they present a logical theory of relations where the unsatisfiability of a formula is equivalent to the model fulfilling a set of assertions.
By transforming the question of $\llbracket M\rrbracket \subseteq \semsof{M_{prop}}$ into $\semsof{M} \cap \overline{\semsof{M_{prop}}} = \emptyset$ and then a formula $ \psi_M \land \neg \psi_{M_{prop}}$ it proves whether the given model is stronger than the condition that is to be tested.
The formula is then decomposed until there exists a satisfying model for the formula or it is deemed unsatisfiable. 

Today there are many open questions in this field of research. Is it possible to automatically verify  more than the rational CAT fragment?
Can the popular models written in CAT be transformed into ones that are written in rational CAT?
Is it possible to verify compiler transformations?
This master's thesis will be about the issue of whether the proof system in \cite{GruMey25} can be improved while sustaining the soundness and completeness. 


\section{Preliminaries}
\subsection{Executions}
Executions consist of a set of all events that occur $E$, the set of initial writes $IW$ and relations that are determined through the program and how it is executed. It is one possible instance of the relations on the memory events that describe how the code is run.
\begin{definition}[Execution]
An execution $X$ is the following tuple:
\[X := (E_X,\po_X \subseteq E_X \times E_X, \rf_X \subseteq W_X \times R_X, IW_X)\]  
We let $\mathbb{E} = \mathbb{P}(X)$ denote the set of all possible executions. \\
Furthermore, for any in CAT constructed relation $\bangle{rel}$, $\bangle{rel}_X$ denotes the instance of it on the execution $X$.
\end{definition}


\subsection{Semantics} \label{sec:semantics}
The semantics of a MCM $M$ can be defined along the definition of the CAT language. In general, they are the set of executions that the model allows.
\begin{definition}[Semantics] \label{def:sem}
Let $M$ be a memory consistency model, $\bangle{cat},\bangle{cat}_1,\bangle{cat}_2$ be CAT expressions and $\bangle{rel},\bangle{rel}_1,\bangle{rel}_2 \subseteq E \times E$ be relations.
\begin{align*}
\semsof{M} & := \semsof{\bangle{cat}} \\
\semsof{\bangle{cat}_1~ \bangle{cat}_2} & := \semsof{\bangle{cat}_1} \cap \semsof{\bangle{cat}_2} \\
\semsof{\texttt{empty}~ \bangle{rel}} &:= \{X \in \E \mid \nexists (e_1,e_2) \in \bangle{rel}_X\} \\
\semsof{\texttt{irreflexive}~ \bangle{rel}} &:= \{X \in \E \mid \forall e \in E_X: \nexists (e,e) \in \bangle{rel}_X \} \\
\semsof{\texttt{acyclic}~ \bangle{rel}} &:= \semsof{\texttt{irreflexive}~ \bangle{rel}^+} \\
\semsof{\bangle{rel}_1.\bangle{rel}_2} &:= \{(e_1,e_2) \mid \exists (e_1,e') \in \bangle{rel}_1 \text{ and } (e',e_2) \in \bangle{rel}_2\} \\
\semsof{\bangle{rel}_1 \cup \bangle{rel}_2} &:= \semsof{\bangle{rel}_1} \cup \semsof{\bangle{rel}_2} \\
\semsof{\bangle{rel}_1 \cap \bangle{rel}_2} &:= \semsof{\bangle{rel}_1} \cap \semsof{\bangle{rel}_2} \\
\semsof{\bangle{rel}_1 \setminus \bangle{rel}_2} &:= \semsof{\bangle{rel}_1} \setminus \semsof{\bangle{rel}_2} \\
\semsof{\sim \bangle{rel}} &:= \{(e_1,e_2) \mid (e_1,e_2) \notin \bangle{rel}\} \\
\semsof{\bangle{rel}^{-1}} &:= \{(e_1,e_2) \mid (e_2,e_1) \in \bangle{rel}\} \\
\semsof{\bangle{rel}^+} &:= \{(e,e') \mid \exists n \in \N: (e,e_1), \dots ,(e_n,e') \in \bangle{rel}\} \\
\semsof{\bangle{rel}?} &:= \semsof{\bangle{rel}} \cup \id \\
\semsof{\bangle{rel}^*} &:= \semsof{\bangle{rel}?} \cup \semsof{\bangle{rel}^+} \\
\semsof{\bangle{base\_set}_1 \times \bangle{base\_set}_2} &:= \{(e,e') \mid e \in \bangle{base\_set}_1, e' \in \bangle{base\_set}_2\} \\
\semsof{\bangle{base\_rel}} &:= \bangle{base\_rel}
\end{align*}
\end{definition}


\section{The Proof System} \label{sec:proofsys}
In order to prove $\semsof{M} \subseteq \semsof{M_{prop}}$ we devise a general method of proving one model to be stronger than another based on inclusion between the relations. For this purpose, we design rules that the expression $\semsof{M} \subseteq \semsof{M'}$ from the statement $true$. The derivation therefore acts according to logical implication, since $true \impl \semsof{M} \subseteq \semsof{M'}$ would mean that the implied part holds. If there is no valid derivation from $true$ to the inclusion that should be proven, then the inclusion cannot hold.
Since there may be multiple branches of reasoning it is important to clarify that every branch needs to start at $true$ in order to verify the inclusion.
It is possible to have a branch start at a $false$ statement, which automatically disproves the inclusion. 


\subsection{Basic Rules}
The most basic rules are those which are always true for any relations. We list them here and sort them by the contributing operators. 
\begin{itemize}
\item Unification $\cup$
\begin{mathpar}
\inferrule*{true}{R \cup R \subseteq R} \and
\inferrule*{true}{R \subseteq R \cup S} \and 
\inferrule*{R \subseteq S}{R \subseteq S \cup R'} \and
\inferrule*{R \subseteq S}{R \cup R' \subseteq S \cup R'} \and
\inferrule*{R \subseteq S \\ R' \subseteq S}{R \cup R' \subseteq S} \and
\inferrule*{R \subseteq S \\ R' \subseteq S'}{R \cup R' \subseteq S \cup S'}
\end{mathpar}

\item Intersection $\cap$
\begin{mathpar}
\inferrule*{true}{R \subseteq R \cap R} \and
\inferrule*{true}{R \cap S \subseteq R} \and 
\inferrule*{R \subseteq S}{R \cap R' \subseteq S} \and
\inferrule*{R \subseteq S}{R \cap R' \subseteq S \cap R'} \and
\inferrule*{R \subseteq S \\ R \subseteq S'}{R \subseteq S \cap S'} \and
\inferrule*{R \subseteq S \\ R' \subseteq S'}{R\cap R' \subseteq S \cap S'}
\end{mathpar}

\item Concatenation $.$
\begin{mathpar}
\inferrule*{true}{R \subseteq S^*.R} \and 
\inferrule*{R \subseteq S}{R'.R \subseteq R'.S} \and
\inferrule*{R \subseteq S}{R.R' \subseteq S.R'} \and
\inferrule*{R \subseteq S \\ R' \subseteq S'}{R.R' \subseteq S.S'}
%\inferrule*{R.R \subseteq R}{R^+ \subseteq R} 
\end{mathpar}

\item Transitive Closure $^+$
\begin{mathpar}
\inferrule*{true}{R \subseteq R^+} \and
\inferrule*{R \subseteq S}{R \subseteq S^+} \and
\inferrule*{R \subseteq S}{R^+ \subseteq S^+}
\end{mathpar}

\item Reflexive Closure $?$
\begin{mathpar}
\inferrule*{true}{\id \subseteq R?} \and
\inferrule*{true}{R \subseteq R?} \and
\inferrule*{R \subseteq S}{R \subseteq S?} \and
\inferrule*{R \subseteq S}{R? \subseteq S?}
\end{mathpar}

\item Reflexive-transitive Closure $^*$
\begin{mathpar}
\inferrule*{true}{R \subseteq R^*} \and 
\inferrule*{true}{\id \subseteq R^*} \and  
\inferrule*{true}{R^+ \subseteq R^*} \and
\inferrule*{true}{R? \subseteq R^*} \and
\inferrule*{R \subseteq S}{R \subseteq S^*} \and
\inferrule*{R \subseteq S}{R^* \subseteq S^*}
\end{mathpar}

\item Difference $\setminus$
\begin{mathpar}
\inferrule*{true}{R\setminus S \subseteq R} \and
\inferrule*{true}{R\setminus R \subseteq 0} \and
\inferrule*{R \subseteq S}{R \setminus R' \subseteq S} \and
\inferrule*{R \subseteq S}{R\setminus R' \subseteq S\setminus R'}
\end{mathpar}

\item Inverse $^{-1}$
\begin{mathpar}
\inferrule*{true}{R^{-1^{-1}} \subseteq R} \and
\inferrule*{R \subseteq S}{R^{-1} \subseteq S^{-1}}
\end{mathpar}

\item Complement $\sim$
\begin{mathpar}
\inferrule*{true}{R~ \cap \sim R \subseteq 0} \and
\inferrule*{R \subseteq S}{\sim S \subseteq \sim R} \and
\inferrule*{R \subseteq S}{R~ \cap \sim S \subseteq 0} \and
\inferrule*{false}{\sim R \subseteq R} \and
\inferrule*{false}{R \subseteq \sim R}
\end{mathpar}
\end{itemize}

\subsection{Eliminating the Constraint}
One important aspect that one has to keep in mind when comparing models is that the constraints \texttt{acyclic}, \texttt{irreflexive} and \texttt{empty} inverse the inclusion of relations.
This means the following:
\begin{lemma}
For any $R_1 \subseteq R_2$ it applies that $\bangle{constraint}~ R_2 \subseteq \bangle{constraint}~ R_1$ when the constraint is the same for each relation.
\end{lemma}
\begin{proof}
We can prove this for each of the constraints. 
Let the constraint be \texttt{empty}:
%$R_1 \subseteq R_2 $ is given. Since this means that any element of $R_1$ would also be in $R_2$, it follows that an empty $R_2$ implies an empty $R_1$. If it would not be empty, then $R_2$ wouldn't be.
%Therefore $\semsof{\texttt{empty}~ R_2}$ must be a subset of $\semsof{\texttt{empty}~ R_1}$.
\begin{eqnarray*}
R_1 \subseteq R_2 
& \impl &\forall X \in \E : (\nexists (e_1,e_2) \in {R_2}_X \impl \nexists (e_1,e_2) \in {R_1}_X) \\
& \impl &(X \in \semsof{\texttt{empty}~ R_2} \impl X \in \semsof{\texttt{empty}~ R_1}) \\
& \impl & \semsof{\texttt{empty}~ R_2} \subseteq \semsof{\texttt{empty}~ R_1}
\end{eqnarray*}
%Let $X$ be an execution with $X \in \semsof{\texttt{empty}~ R_2}$ and $X \notin \semsof{\texttt{empty}~ R_1}$ and therefore $\semsof{\texttt{empty}~ R_2} \nsubseteq\semsof{\texttt{empty}~ R_1}$. Since $R_1 \subseteq R_2$, it means that ${R_1}_X \subseteq {R_2}_X$ and if $R_2$ is empty then $R_1$ has to be as well. Therefore $X$ cannot exist and $\semsof{\texttt{empty}~ R_2} \subseteq \semsof{\texttt{empty}~ R_1}$.
For the constraint \texttt{irreflexive}:
\begin{eqnarray*}
R_1 \subseteq R_2 
& \impl &\forall X \in \E : (\forall e \in E_X: \nexists(e,e) \in {R_2}_X \impl \forall e \in E_X: \nexists (e,e) \in {R_1}_X) \\
& \impl &(X \in \semsof{\texttt{irreflexive}~ R_2} \impl X \in \semsof{\texttt{irreflexive}~ R_1}) \\
& \impl & \semsof{\texttt{irreflexive}~ R_2} \subseteq \semsof{\texttt{irreflexive}~ R_1}
\end{eqnarray*}

For the \texttt{acyclicity} constraint:
\begin{eqnarray*}
R_1 \subseteq R_2 
& \impl &\forall X \in \E : (\forall e \in E_X: \nexists(e,e) \in {R_2}_X^+ \impl \forall e \in E_X: \nexists (e,e) \in {R_1}_X^+) \\
& \impl &(X \in \semsof{\texttt{acyclic}~ R_2} \impl X \in \semsof{\texttt{acyclic}~ R_1}) \\
& \impl & \semsof{\texttt{acyclic}~ R_2} \subseteq \semsof{\texttt{acyclic}~ R_1}
\end{eqnarray*}
\end{proof}
This lemma generates the following three rules:
\begin{mathpar} 
\inferrule*[left=(empty)] {R_1 \subseteq R_2}{\semsof{\texttt{empty}~ R_2} \subseteq \semsof{\texttt{empty}~ R_1}} \and 
\inferrule*[left=(acyclic)] {R_1 \subseteq R_2}{\semsof{\texttt{acyclic}~ R_2} \subseteq \semsof{\texttt{acyclic}~ R_1}} \and
\inferrule*[left={(irreflexive)}] {R_1 \subseteq R_2}{\semsof{\texttt{irreflexive}~ R_2} \subseteq \semsof{\texttt{irreflexive}~ R_1}}
\end{mathpar}

Since not every inclusion offers the comfort of having both models use the same constraint, they need to be converted. For this purpose there are some rules:

\begin{lemma}
For a relation $R$, it holds that $\semsof{\texttt{irreflexive}~ R^+} = \semsof{\texttt{acyclic}~ R}$.
\end{lemma}
\begin{proof}
This is given via the \Cref{def:sem} of $\semsof{\texttt{acyclic}~ \bangle{rel}}$.
\end{proof}

\begin{lemma}
For any relation $R$ it holds that $\semsof{\texttt{empty}~ R} = \semsof{\texttt{irreflexive}~ R.R^-1}$.
\end{lemma}
\begin{proof} This can equally be proven using \Cref{def:sem}.
\begin{eqnarray*}
\semsof{\texttt{empty}~ R} &=& \{X \in \E \mid \nexists (e_1,e_2) \in R_X\} \\
&=& \{X \in \E \mid \forall e \in E_X: \nexists (e,e') \in R_X\} \\
&= & \{X \in \E \mid \forall e \in E_X: \nexists (e,e) \in R_X.R_X^{-1} \} \\
&=& \semsof{\texttt{irreflexive}~ R.R^{-1}}
\end{eqnarray*}
\end{proof}

\begin{lemma}
For any relation $R$ it holds that $\semsof{\texttt{empty}~ R} = \semsof{\texttt{acyclic}~ R \cup R^{-1}}$.
\end{lemma}
\begin{proof}
\begin{eqnarray*}
\semsof{\texttt{empty}~ R} &=& \{X \in \E \mid \nexists (e_1,e_2) \in R_X\} \\
&=& \{X \in \E \mid \forall e \in E_X: \nexists (e,e') \in R_X \} \\
&=& \{X \in \E \mid \forall e \in E_X: \nexists (e,e) \in R_X \cup R_X^-1 \} \\
&=& \semsof{\texttt{acyclic}~ R \cup R^{-1}} \\
\end{eqnarray*}
\end{proof}
